# 开发规范（Docs-First）

> **强制约定**：本项目所有步骤（里程碑）、功能变更、接口/规则调整，**必须先完成软件工程文档，经确认（或按约定自检通过）后，方可编写/修改业务代码**。  
> 违反顺序的实现视为无效，应先补文档再合入。

---

## 1. 核心原则

| 原则 | 说明 |
|------|------|
| **文档先行** | 设计 / 规格 / 验收标准先落盘，再写代码 |
| **小步可验收** | 每个里程碑或变更有明确 Done 标准 |
| **轮次收尾** | 每轮任务结束后必须输出「已完成总结 + 下一步完整清单」（见 §2.1） |
| **跨机基线落盘** | 每轮结束必须更新仓库内进度文档；**不以 chat session 为跨电脑状态源**（见 §2.2） |
| **权威单一** | 规则与状态以 `engine/` 为准；文档描述与代码冲突时，**先改文档对齐决议，再改代码** |
| **可复现** | 涉及 `game_id`、随机、计分的行为必须在文档中写明种子与序列化约定 |
| **可追溯** | 变更有编号、状态、关联里程碑或 ADR |

## 2. 标准工作流

```
需求 / 里程碑 / Bug
        │
        ▼
┌───────────────────┐
│ 1. 选型文档类型    │  见 §3
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 2. 撰写/更新文档   │  模板见 §4
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 3. Review 文档     │  用户确认 或 对照清单自检
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 4. 实现代码 + 测试 │  严格按文档范围，不扩 scope
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 5. 对照验收清单    │  文档 §验收 全部勾选
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 6. 回写文档        │  实现偏差、API 终稿、状态 → Done
└─────────┬─────────┘
          ▼
┌───────────────────┐
│ 7. 轮次收尾报告    │  对话总结（§2.1）+ **仓库文档落盘**（§2.2）
└───────────────────┘
```

### 2.1 每轮任务收尾报告（强制 · 对话内）

**「一轮任务」**定义：用户一次明确委托的闭环工作（例如：写 M01 规格、实现 M01、修某个 bug、新增一条开发规则）。助手在该轮**最后一条回复**中必须包含以下两块，不得省略。

#### A. 本轮已完成情况

| 项 | 要求 |
|----|------|
| 目标回顾 | 本轮要解决什么 |
| 交付物 | 文档路径 / 代码路径 / 测试结果（有则列，无则写「无」） |
| 状态变更 | 相关里程碑/功能文档状态（如 Draft → Review） |
| 未完成/偏差 | 计划内未做完的、或与规格的差异 |
| 风险/阻塞 | 若有 |

#### B. 下一步完整任务清单

须给出**可执行、有序**的清单，而不是一句「继续 M2」：

1. **立即下一步**（用户一句指令即可启动的 1 项，写清动作与产出）  
2. **后续完整队列**（从当前进度到近期目标的全量步骤，建议含：文档 → 确认 → 实现 → 验收）  
3. 每项尽量包含：`动作` · `产出物路径` · `依赖` · `建议触发语`（如「确认 M01」「实现 M01」）  
4. 队列应覆盖 **当前里程碑剩余工作 + 下一里程碑入口**，并与 `docs/milestones/README.md` / `PLAN.md` 路线图一致  
5. 若本轮仅改流程文档，清单中仍要指明**产品开发主线**的下一项  

**禁止**：

- 轮次结束只改文件、不在回复中总结  
- 「下一步」只有空泛表述、无可执行清单  
- **只在对话里总结、不写仓库文档**（违反 §2.2）  

**禁止**（通用）：

- 无规格直接写功能代码  
- 实现时静默改变规则/接口而不更新文档  
- 把多个里程碑揉进一次无边界的大改  

**允许不经完整规格的例外**（仍建议一行说明记入 `docs/changelog.md`，且仍须更新 `LATEST.md`）：

- 纯错别字、注释、格式  
- 不改变行为的重命名（若为公开 API，仍须更新接口文档）  
- 测试用例补充且不断言新需求  

### 2.2 每步文档落盘 / 跨机同步基线（强制 · 仓库内）

#### 目的

用户可能在 **不同电脑 / 不同 AI session** 继续开发。Chat 历史**不保证**同步或保留。  
**唯一可靠基线 = 仓库内 `docs/`（随 OneDrive/git 同步的文件）**。

#### 每轮结束必须落盘（最低集）

| 文件 | 何时 | 动作 |
|------|------|------|
| [`docs/status/LATEST.md`](status/LATEST.md) | **每一轮**闭环结束 | **覆盖写**为当前基线：日期、本轮摘要、功能线状态、锚点数字、**下一步队列**、风险 |
| [`docs/changelog.md`](changelog.md) | 有实质交付（实现/规格状态变更/评估结论/流程规则变更） | **追加**倒序条目（人可读摘要 + 路径） |
| 相关规格 `docs/features/` 或 `docs/milestones/` | 需求/范围/状态变了 | 更新正文与状态栏 |
| `docs/status/YYYY-MM-DD.md`（可选） | 需要保留日终长文 | 追加/新建；**不替代** `LATEST.md` |

> **最低要求**：哪怕本轮「只改了一处 bug」或「只写了流程规则」，也必须刷新 `LATEST.md`，使下一台机器打开仓库后只读该文件即可接续。

#### 新会话 / 换机开工（强制读序）

助手在**无可靠对话上下文**或用户声明 session 未同步时，必须先读：

1. `docs/status/LATEST.md`  
2. `docs/changelog.md`（最近日期段）  
3. 与当前任务相关的 `docs/features/*` / `docs/milestones/*` 状态栏  

读毕在回复中用简短「已同步基线」确认（可点出当前主线与立即下一步），再执行用户新指令。

#### 禁止

- 把「session 里说过」当作已合入事实，却未写入 `docs/`  
- 只更新代码、changelog 不写、`LATEST` 过期  
- 用口头「下次记得」代替落盘  

#### 与 Docs-First 的关系

- §2.2 **不替代**「先规格后代码」；它补的是 **进度与决策的可迁移性**。  
- 规格仍按 §3–§4；进度基线走 `status/` + `changelog.md`。

## 3. 文档类型与目录

```
docs/
├── DEVELOPMENT.md           # 本规范（流程权威）
├── changelog.md             # 面向人的变更摘要（有实质交付时追加）
├── status/                  # 跨机进度基线（§2.2）
│   ├── LATEST.md            # 每轮覆盖写 · 换机先读
│   └── README.md
├── architecture/            # 跨模块架构（总览可链到根目录 PLAN.md）
│   └── README.md
├── milestones/              # 里程碑规格（M1, M2, …）
│   └── Mxx_<slug>.md
├── features/                # 非里程碑的功能变更 / 增强
│   └── Fxxxx_<slug>.md
├── adr/                     # 架构决策记录（重大取舍）
│   └── NNNN-<slug>.md
└── api/                     # 稳定接口说明（实现后或规格中定义）
    └── *.md
```

根目录保留：

| 文件 | 角色 |
|------|------|
| `PLAN.md` | 系统级总设计（产品与架构基线） |
| `assets/ASSETS.md` | 图形资源契约 |
| `docs/DEVELOPMENT.md` | **开发流程权威** |

`PLAN.md` 描述「做什么、系统怎么拆」；`docs/milestones/*` 描述「本步具体交付与验收」；冲突时以 **已确认的里程碑/ADR** 为准，并回写 `PLAN.md`。

## 4. 文档模板要求

### 4.1 里程碑规格 `docs/milestones/Mxx_*.md`

必须包含：

1. **元信息**：编号、标题、状态（`Draft` / `Review` / `Approved` / `In Progress` / `Done`）、依赖的上一里程碑  
2. **目标**：本步解决什么问题（3–8 句）  
3. **范围**：In Scope / Out of Scope  
4. **设计**：模块、类/函数职责、数据流、与 `PLAN.md` 的对应关系  
5. **接口与数据**：公开 API、JSON 字段、配置项（可先伪代码）  
6. **文件清单**：计划新增/修改的路径  
7. **测试计划**：单元/集成用例列表  
8. **验收标准**：可勾选 checklist  
9. **风险与开放问题**：未决项不得标 `Approved`  

**状态门禁**：

- `Draft` → 可改文档，不可写业务代码  
- `Review` → 等待确认  
- `Approved` → **允许**按文档写代码  
- `In Progress` → 编码中  
- `Done` → 验收通过 + 文档回写完成  

### 4.2 功能变更 `docs/features/Fxxxx_*.md`

适用于：里程碑之外的增强、规则补丁、UI 调整、Reward 新字段等。

必须包含：背景、动机、方案、影响面（引擎/玩家/训练/资源）、兼容性、验收、回滚思路。

编号建议：`F0001` 起递增。

### 4.3 架构决策 ADR `docs/adr/NNNN-*.md`

适用于：进程模型、通信协议、规则默认值变更、存储格式 breaking change 等。

建议结构：

- 状态：Proposed / Accepted / Deprecated  
- 上下文  
- 决策  
- 后果（正/反）  
- 替代方案  

### 4.4 实现后回写

编码完成后必须更新：

- 里程碑/功能文档状态 → `Done`  
- 「实现备注」：与规格的差异（若有）及原因  
- `docs/changelog.md` 一条摘要  
- 若改变系统级约定 → 同步 `PLAN.md` 对应章节

## 5. 与里程碑路线图的关系

基线路线图见 `PLAN.md` §11。执行顺序：

| 步骤 | 动作 |
|------|------|
| 1 | 撰写 `docs/milestones/M01_....md`（或当前 Mx） |
| 2 | 用户 Review → `Approved` |
| 3 | 编码 + 测试 |
| 4 | 验收 → `Done`，再进入 M(x+1) 文档 |

**不得**跳过文档直接进入下一里程碑编码。

---

## 6. 协作约定（人 / AI 助手）

1. 用户说「开始 Mx」时：助手 **先检查** 是否存在状态为 `Approved` 的里程碑文档；若无，**只写文档**，不写业务代码。  
2. 用户说「实现 / Build / 写代码」且文档已 `Approved`：按文档范围实现。  
3. 用户提出新功能：助手 **先** 建 `docs/features/...` 或 ADR，再等确认。  
4. 发现规格错误：先改文档并标注，再改代码。  
5. 每次交付说明中应指向：**文档路径 + 代码路径 + 验收结果**。  

---

## 7. 代码层最低要求（在文档批准之后）

- 目录与职责遵守 `PLAN.md`（`engine/` 权威、`players/` 可插拔）  
- 公开行为有测试（与里程碑「测试计划」对齐）  
- 不引入未在文档声明的依赖（当前已批准：`pygame`、`numpy`）  
- Human 玩家：子进程隔离（已决议）  
- 日志与 `game_id` 复现约定不得无文档变更而更改  

---

## 8. 快速检查清单（开工前）

- [ ] 存在对应里程碑或功能文档  
- [ ] 状态为 `Approved`（或用户当条消息明确「按此文档实现」）  
- [ ] In/Out Scope 清晰  
- [ ] 验收标准可测试  
- [ ] 未决开放问题已关闭或显式延期  
- [ ] 与 `PLAN.md` / 已有 ADR 无未说明的冲突  

---

## 9. 修订本规范

对本文件的修改本身即流程变更：提交简短说明（可写在 `docs/changelog.md`），重大变更建议同时增加 ADR。
