## 1. 结论

现有 96 行**不适合作为 96 个独立开发和验收单元直接沿用**。它们最初适合做章节级差距盘点，但其中多数是“能力簇”或“模块容器”，常把权威规则、确定性算法、人类化启发式、概率/训练模型、状态生命周期和审计指标放在同一行。若继续沿用，一项粗粒度测试通过会掩盖同一行内其他 hard 子断言未实现。

重构结果：

| 处置 | 旧项数量 | 含义 |
|---|---:|---|
| KEEP | 8 | 原边界已接近单一职责 |
| SPLIT | 56 | 含多个职责、方法类别或状态转换 |
| MERGE | 9 | 与相邻项重复或只是同一生命周期的片段 |
| RENAME | 20 | 边界可保留，但名称误导或未体现方法类别 |
| REMOVE | 3 | 治理/汇总结论，无独立运行输入输出 |
| ADD | 4 | 锁定来源要求存在，但旧 96 行没有独立单元 |
| **新目录** | **96** | 16 RULE + 11 ALGO + 23 HEUR + 5 MODEL + 12 STATE + 6 SCORE + 9 TRAIN + 14 AUDIT |

新目录总数也是 96 仅属巧合。它不是旧 ID 的重编号：56 个旧项被拆分，多项新单元吸收多个旧项，另有 4 个新增单元。

## 2. 审查方法

每个 AU 行按以下顺序复核：

1. 从两份锁定来源定位章节语义，不把原审计名称当权威边界。
2. 读取矩阵中的目标、GP/RP、实现符号、调用方、测试、证据等级和缺口。
3. 对照当前模块所有权：
   - `engine/`：权威规则、状态、计分、持久化、事件；
   - `protocols/`：PlayerView 与子进程/线协议；
   - `players/humanlike/`：算法、启发式、认知、概率近似；
   - `training/`：观测、动作、奖励、episode 与环境；
   - `tests/humanlike_v2/` 及 `tests/test_*.py`：当前直接/集成证据候选。
4. 用七项标准检查单一职责、输入输出、独立测试、独立运行证据、重复、方法混合和复合状态转换。
5. 先确定新单元职责，再建立 old→new many-to-many 映射；不为了保持 96 而拼接单元。

本轮是边界审查，不重判矩阵的实现状态，不运行测试，也不把候选测试名称提升为证据。

## 3. 主要边界问题

### 3.1 规则和策略混在一起

典型项包括 AU-010、AU-013、AU-032～AU-038、AU-040。比如 AU-033 同时包含杠资格、抢杠状态转换、杠分和 AI 是否愿意杠；这些分别属于 RULE-008/009、SCORE-003 和 HEUR-013，失败含义完全不同。

### 3.2 确定性算法和概率模型混在一起

AU-023、AU-050、AU-075 把“可见/未见牌的确定性计数”“墙内活牌估计”“逐对手假设分布”“点炮损失风险”视作一个能力。新目录分别建立 ALGO-003/004、MODEL-001/002，避免用计数正确性替代概率校准。

### 3.3 模块容器被当作功能单元

AU-054～AU-063、AU-085、AU-093 多按架构模块命名。模块可包含多个独立职责，不能整体判定 Passed。Rule Engine 被拆为具体状态转换；Humanlike Policy 被拆为算法、启发式和模型；架构/接口本身合并为 AUDIT-013 契约审计。

### 3.4 测试清单和完成定义被当作产品能力

AU-088 是测试项目清单，AU-094 是实施顺序，AU-096 是全局完成定义。AU-088 合并为 AUDIT-006 证据门禁；AU-094/096 从功能目录移除，分别保留在开发计划和发布门禁语境。它们不能拥有一个运行输入并输出业务结果。

### 3.5 一个单元包含多个状态转换

AU-032 同时包含胡资格、过胡和强制胡；AU-033 同时包含三种杠和抢杠；AU-040 同时包含多类终局调整；AU-071/072 覆盖整个状态机。新 RULE/STATE/SCORE 单元按可触发的原子状态转换重切，允许每项单独失败而不被汇总通过掩盖。

## 8. 代码与测试结构适配

新分类与当前目录大体兼容，但不以现有文件边界反推职责：

- RULE/STATE/SCORE 当前主要落在 `engine/legal.py`、`engine/blood_battle.py`、`engine/opening.py`、`engine/state.py`、`engine/score.py`；一个文件可实现多个新单元。
- ALGO/HEUR/MODEL 当前主要分布于 `players/humanlike/`、`protocols/player_view_*.py` 和部分 `engine/`；同一管线中的方法分类必须在规格和证据中分开。
- TRAIN 对齐 `training/action_codec_v2.py`、`observations_v2.py`、`reward_v2.py`、`env.py`，但多智能体、离线训练和模型生命周期仍可为 Not Evaluated。
- AUDIT 对齐 `engine/audit.py`、`engine/replay.py`、`training/metrics_v2.py` 及测试/验收产物；测试文件存在不等于单元通过。
- 当前测试按文件/历史功能组织，尚未按新 ID 组织。后续应在测试 metadata 或 trace matrix 中映射新 ID，而不是立即重命名所有测试文件。

## 9. 验收边界要求

每个新单元进入详细规格时必须至少冻结：

- 单一 method class；
- 输入 schema、状态所有者和输出/错误行为；
- 至少一个正例、反例和边界场景；
- 实现候选符号与直接测试断言；
- 最低 EV 等级及保留产物；
- 对外部数据依赖使用 Not Evaluated，不用工程测试替代；
- hard 规则不允许平均抵消。

## 10. 一致性与限制

- `unit_migration_map.csv` 共 100 行数据：96 个旧 AU + 4 个 ADD。
- 96/96 个旧 AU 均有明确处置；除 3 个 REMOVE 外均映射到至少一个新 ID。
- 建议目录含 96 个唯一新 ID；每个新 ID 都至少被一个旧项或 ADD 项映射。
- 本轮未执行 pytest、coverage、批跑或效果评估，未改变旧矩阵状态/证据等级。
- 本轮未修改代码、测试、配置或两份锁定来源。
