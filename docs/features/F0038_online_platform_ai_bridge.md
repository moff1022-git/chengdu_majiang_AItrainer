| #   | 结论                                                                                                                                  |

## 1. 背景与目标

### 1.1 背景

本仓库是 **成都麻将 · 血战到底** 本地权威引擎 + 可插拔 AI/人类 + UI + 训练与 Humanlike v2 策略。`PLAN.md` 首版 **非目标**含网络多人实时对战服务器。用户要求评估：如何将现有 AI **接到线上主流平台并自动玩牌**。

### 1.2 文档目标

| ID | 目标 |
|----|------|
| G1 | 梳理当前**线上主流血战到底/川麻对战**形态与代表产品 |
| G2 | 分析 AI 自动接入的**技术路径、成本、风险** |
| G3 | 给出与本项目架构对齐的**分层方案与阶段路线** |
| G4 | 明确 **In / Out of Scope** 与合规边界 |

### 1.3 非目标

- 不提供任何商业 App 的逆向协议、破解、注入、批量脚本 PoC  
- 不承诺「挂机打金」或绕过反作弊  
- 本轮**不写业务代码**（待 `Approved` 且选定路径后再开实现 F/M）

## 2. 线上平台调研（公开信息）

> 棋牌市场迭代快；以下为公开应用商店/官网/百科/技术文章归纳，**非**精确市场份额。

### 2.1 产品形态

| 类型 | 特征 | 与血战到底 |
|------|------|------------|
| A. 国民级合集 App | 大 DAU、3D 牌桌、多地方玩法、真人对战 | 常含四川**血流/血战** |
| B. 川麻垂直 / 小游戏 | 微信小游戏、独立 App、方言 | 更贴近四川本地规则 |
| C. 竞技赛事向 | 赛制、奖金/积分 | 如 JJ 麻将赛事 |
| D. 单机 / 弱联网 | 本地 AI | 非主流「线上对战」 |
| E. 国际/日麻平台 | 天凤、雀魂 | **规则非川麻**；AI 协议生态可作架构参考 |

### 2.2 代表平台

| 平台 / 产品 | 运营（公开） | 模式要点 | 对第三方 AI 接入（公开层） |
|-------------|--------------|----------|----------------------------|
| **欢乐麻将全集** | 腾讯 | 真人对战；四川血流/血战、打缺门、刮风下雨等 | **无公开 Bot API**；强反作弊预期 |
| **JJ 麻将** | 竞技世界 | 含四川血战等地方玩法；赛事 | 同上 |
| **四川麻将血战到底（微信小游戏等）** | 多家 | 轻量社交房 | 闭源加密常见 |
| **人人麻将** 等 | 独立发行 | 血流/血战/红中等 | 闭源 |
| **禅游等渠道川麻 App** | 禅游等 | 定缺、一胡到底等 | 闭源 |
| **蜀山四川麻将** 等 | 区域棋牌 | 好友房、血流红中 | 闭源 |
| **兜来玩麻将**（快手案例） | 快手 | 血战/血流等；**平台自研 AI** 填匹配/代打 | **内部能力**，非第三方 SDK |
| **天凤 / 雀魂** | 日麻生态 | Suphx、Mortal、MahjongCopilot | 有研究/第三方协议；**规则不适配本引擎** |

检索结论：**无面向个人开发者的「成都血战官方实时出牌 Bot SDK」**。

### 2.3 行业技术共性

```text
客户端 → 加密长连接/WS → 网关+反作弊 → 房间/匹配/结算 → 服务端权威状态
```

- 服务端权威（与本项目 `engine/` 角色类似，但状态在对方）  
- 私有协议与动作编码 ≠ 本仓库 `Action` / `GameState`  
- 反作弊：时序、多开、脚本特征、设备指纹  
- 同名「血战」在换三张、封顶、查叫、杠分上可能与本引擎配置有差异

## 4. 方案矩阵

### 4.1 统一抽象

```text
 Policy (rule_ai / humanlike / 人类)
        ▲ ActionRequest / Decision
 OnlineBridge / Adapter
        ▲
 SelfHostRoom | Official API | （禁止）逆向客户端
```

**决策层不依赖 UI；Adapter 负责观测翻译与动作回写。**

### 4.2 方案 A — 自建线上对战（**推荐主路径**）

| 项 | 内容 |
|----|------|
| 思路 | 房间服 + 客户端；权威=`engine`；席位接 AI/人类 |
| 自动玩牌 | 全 AI 或 1 人 3 AI，天然合规 |
| 优点 | 规则一致、可复现 `game_id`、可产训练日志 |
| 缺点 | 无现成 DAU |
| 粗估 | 好友房 MVP 数周；公网匹配数月 |

子路径：**A1 局域网/好友房** → **A2 公网匹配**。

### 4.3 方案 B — 官方/商务合作

| 项 | 内容 |
|----|------|
| 思路 | 厂商提供匹配填充/掉线代打 API；本侧只跑 Policy 服务 |
| 先例 | 快手等业务内多玩法麻将 AI（公开分享，**非**对外开放） |
| 优点 | 合规商用 |
| 缺点 | 商务门槛 |

建议接口形态：`observation + legal_actions → action`（规则集 ID 必填）。

### 4.4 方案 C — 教练 / 旁路 HUD（主写：观测与采集）

| 项 | 内容 |
|----|------|
| 思路 | **不代用户点击出牌**；只根据「人类玩家可见的公开/私有信息」给出推荐（对齐 F0011 / Humanlike 决策） |
| 对照 | 日麻生态「指导 HUD」形态（架构参考；对接商业客户端可能仍触及 ToS，产品需免责） |
| 定位 | **教学 / 复盘 / 训练数据采集**；与方案 D/E 外挂切割 |
| 核心输入 | ① 对手弃牌序列 ② 各家副露 ③ 自家手牌（+ 可选：定缺、墙剩余、当前阶段） |
| 核心输出 | 推荐出牌 / 碰杠胡建议 + 理由；可选 JSONL 采集日志 |

#### 4.4.1 要采集的三类信息（与本项目 view 对齐）

教练 AI 并不需要对方服务器的完整 `GameState`，只需 **座位视角** 下人类本就可看见的字段。映射到本仓库 `PlayerView` / `build_observation` 习惯：

| 信息类 | 可见性 | 建议内部结构（逻辑牌 ID，如 `3w`/`9p`/`1s`） | 用途 |
|--------|--------|-----------------------------------------------|------|
| **自家手牌** | 仅自己可见 | `self.hand: list[str]`（13 或 14 张，已排序可选） | 向听、进张、推荐出牌、防放炮 |
| **对手弃牌** | 公开 | `players[s].discards: list[str]`（按时间序） | 读河、危险度、F0010 类推断 |
| **各家副露** | 公开（含自己） | `players[s].melds: list[{type, tiles}]` | 牌山剩余、形状、是否门清 |
| （强烈建议）定缺 | 公开或半公开 | `players[s].dingque: "wan"\|"tong"\|"tiao"\|null` | 川麻必备 |
| （建议）最后打出 | 公开 | `last_discard` + `last_discard_seat` | 响应阶段（碰/杠/胡） |
| （可选）墙剩余 | 公开 UI 常有 | `wall_remaining: int` | 中后期策略 |
| （可选）阶段 | 推断或录入 | `phase: exchange\|dingque\|discard\|response\|…` | 调用哪类 decide |

**不采集 / 不猜测进模型输入的：** 对手未公开手牌、牌山精确顺序、对方客户端私有协议字段。

#### 4.4.2 可行性总表（2026-08 修订：C1 主路径）

| 采集通道 | 自家手牌 | 对手弃牌 | 副露 | 准确率潜力 | 实时性 | 合规/ToS | 工程难度 | **当前定位** |
|----------|----------|----------|------|------------|--------|----------|----------|--------------|
| **C0 手动录入** | 高 | 高 | 高 | ★★★★★ | 过慢 | 最好 | 低 | **仅兜底**：识别失败时改一张牌；**不作日常主流程**（实操负担大，用户判定不可行） |
| **C1 区域截图 + 视觉识别** | 中→高 | 中→高 | 中 | ★★★☆→★★★★（单皮肤+标定） | 目标 0.5–1.5s/刷新 | 只读屏幕、不注入；**用户自担目标游戏 ToS** | 中高 | **方案 C 主实现路径** |
| **C2 本项目旁路** | 完美 | 完美 | 完美 | ★★★★★ | 实时 | 完全合规 | 低 | **算法/HUD 回归台架**；不替代外站采集 |
| **C3 官方 API** | 视接口 | 视接口 | 视接口 | ★★★★★ | 实时 | 合规 | 商务 | 远期 |
| **C4 协议/内存** | — | — | — | — | — | **禁止** | — | Out of Scope |

**可行性结论（修订）：**

1. 决策层仍只消费 `CoachObservation`；**外站实操必须靠自动/半自动感知**，故 **C1 为主**。  
2. C0 降级为「单牌纠错 / 定缺点击 / 副露类型确认」等 **点状交互**，禁止依赖「整副牌手动点完」。  
3. C2 用于：在本项目 UI 上验证 Policy/HUD；合成截图训练识别器；不解决欢乐麻将等外站画面。  
4. C1 技术风险集中在 **皮肤差异、3D 透视、动画中间帧、多分辨率**；通过 **每客户端 Layout Profile + 自有 `assets/tiles` 作域适应起点 + 低置信停手** 可控。

#### 4.4.3 目标数据模型（CoachObservation v0）

```text
CoachObservation
├── schema: 1
├── ruleset_id: "chengdu_blood_v1"
├── self_seat: 0..3
├── phase: "discard" | "response" | "dingque" | "exchange" | ...
├── wall_remaining: int | null
├── last_discard: tile_id | null
├── last_discard_seat: int | null
└── players: [0..3]
      ├── seat: int
      ├── dingque: suit | null
      ├── hand: [tile_id]          # 仅 self_seat 非空；他家 [] 或省略
      ├── discards: [tile_id]      # 时间序
      ├── melds: [{ "kind": "peng"|"chi"|... , "tiles": [tile_id] }]
      └── hand_count: int | null   # 他家仅公开张数时
```

与本项目衔接：

| 步骤 | 动作 |
|------|------|
| 1 | `CoachObservation` → 尽量填满 legacy `view` dict（与 `filter_state_for_seat` 字段同构的子集） |
| 2 | 由 **轻量合法性模块** 在「已知公开信息」下枚举可行动作（出牌=手牌任一；响应=对 `last_discard` 的碰/杠/胡/过）——**不要求**完整引擎权威状态 |
| 3 | 构造 `ActionRequest` → 调用 `rule_ai` / Humanlike / F0011 顾问 |
| 4 | HUD 只展示 `Decision` + 理由；**不**写回外部游戏 |

> 完整 `engine.GameState` 在 C0/C1 下**通常无法重建**（缺墙与他手）。因此方案 C 的 Policy 应支持 **「部分观测模式」**：输入不完整时降级（仅向听/危险度启发式），禁止假装拥有 oracle。

#### 4.4.4 三类信息的采集细则

**A. 自家手牌**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 点选面板 | 27 种牌（万筒条 1–9）棋盘 + 张数；支持「摸打同步」：摸一张 / 打一张 | 用户点错 |
| C0 快捷 | 导入字符串 `123m456p789s11m` 类编码 | 编码约定要固定 |
| C1 视觉 | 标定「手牌条」ROI；模板匹配 / 分类器识别每张牌面；14 张时含摸牌位 | 遮挡、金框、缩放、主题皮肤 |
| C2 | 直接读 `build_observation(...).view` 中 self hand | 无 |

**B. 对手弃牌（河）**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 | 四家河分区；每打出一张点一次，或批量「追加弃牌」 | 漏记、顺序错 |
| C0 事件流 | 只记「当前打出」+ 自动 append 到对应 seat | 用户忘点「谁打的」 |
| C1 | 标定三家/四家弃牌区 ROI；检测新增牌面相对上一帧 diff | 动画飞牌、重叠、缩略 |
| C2 | `players[s].discards` 全量 | 无 |

**C. 副露**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 | 选择 seat + 类型（碰/明杠/暗杠/直杠）+ 相关牌 | 暗杠显示因平台而异 |
| C1 | 副露区 ROI；识别副露块数量与牌面；类型用布局启发式（3 张碰 / 4 张杠） | 暗杠牌背、方向 |
| C2 | `players[s].melds` | 无 |

**公开信息一致性校验（采集后必跑）：**

| 校验 | 规则（血战 108 张） |
|------|---------------------|
| 张数守恒 | 每张逻辑牌全局可见计数 ≤ 4 |
| 手牌张数 | 行牌中自己通常 13 或 14；与 phase 一致 |
| 副露耗牌 | 碰 3、杠 4 等从「可能剩余」中扣除 |
| 弃牌不回手 | 已进河的牌不应再出现在 self.hand（用户修正时警告） |

#### 4.4.5 推荐架构（方案 C，**C1 为主**）

└──────────────────────────────▲────────────────────────────────────┘
                               │ CoachObservation + confidences
┌──────────────────────────────┴────────────────────────────────────┐
│  Normalize + Validate + EventLog                                  │
│  tile_id 统一 · 108 守恒 · phase 推断 · 河/副露单调追加              │

┌──────────────────────────────┴────────────────────────────────────┐

**硬规则：** Capture → Policy → HUD **单向**；**禁止**自动点击 / 注入 / 改内存。

#### 4.4.11 C1 实现路径（详细）

##### A. 目标与成功标准

| ID | 目标 | 成功标准（首发「单平台单分辨率」） |
|----|------|-------------------------------------|
| G-C1-1 | 自动得到自家手牌 | 固定皮肤下 top-1 **≥ 95%** 张级准确；整手 13/14 张全对 **≥ 80%** 帧 |
| G-C1-2 | 自动维护对手弃牌河 | 新进河牌检出率 **≥ 90%**；错 seat **&lt; 5%**（可标定纠正） |
| G-C1-3 | 自动维护副露 | 块检出 **≥ 85%**；牌面 **≥ 90%**；kind 自动对 **≥ 70%**，其余一键确认 |
| G-C1-4 | 刷新延迟 | 稳定态 p95 **≤ 1.5s**（不含用户确认） |
| G-C1-5 | 安全 | 零自动出牌；截图默认本机；无隐蔽进程 |

**首发约束（降低难度）：** 先支持 **一种目标客户端 + 一种分辨率/窗口化预设**（例如用户常用的 1080p 窗口），再扩展 profile。

**标定工具流程（用户 2–5 分钟一次）：**

1. 截一张稳定牌桌全屏/窗口图。  
2. 依次拖拽矩形：手牌 → 自己河 → 三家河 → 四家副露（可跳过空区）。  
3. 点 2–3 张手牌中心，估算单牌宽高。  
4. 保存 profile；之后同分辨率一键加载。  

窗口拖动/改分辨率 → 提示「ROI 漂移，请重新标定或启用相对锚点（进阶）」。

##### D. 截帧管线

| 项 | 建议 |
|----|------|
| 频率 | 稳定态 **2–5 fps**；检测到动画（帧差大）时升到 8–10 fps，动画结束后再解析 |
| 触发 | 定时 + 「用户点刷新」手动键 |
| 权限 | macOS：屏幕录制；Windows：桌面复制 API |
| 多屏 | profile 记 `monitor_index` 或窗口 HWND（仅定位，不注入） |
| 隐私 | 帧默认内存环形缓冲（N=30）；**仅用户导出时**落盘；不上传 |

**动画门控：** 对 ROI 算平均绝对差；超过阈值则标记 `unstable=true`，本帧不更新河/副露（避免飞牌中间态）。

##### E. 牌面识别：检测 + 分类（两段式）

**E1 检测（哪里有一张牌）**

| 策略 | 适用 | 说明 |
|------|------|------|
| 固定网格 | 手牌条近似等距 | 按 `hand_approx_w` 切条，最快 |
| 模板峰值 | 河/副露不规则 | 用通用「牌轮廓/亮边」或平均牌模板做 NMS |
| 连通域 | 深色桌+浅色牌 | 阈值分割后外接矩形过滤宽高比 |

输出：`list[BBox]`，附 `region_tag`（hand / river_sK / meld_sK）。

**E2 分类（是哪张逻辑牌）**

| 阶段 | 方法 | 训练数据 |
|------|------|----------|
| **冷启动** | 多尺度模板匹配 / ORB+投票；模板可先用本仓库 `assets/tiles/{wan,tong,tiao}/tile_*_{green,blue}.png` **仅作开发对照** | 真实目标 App 需 **用户导出 50–200 张裁切样例** 建「目标皮肤库」 |
| **主用** | 27 类（万筒条 1–9）+ 可选「牌背/未知」；HSV/边缘归一化后 NCC 或小 embedding | 按 profile 的 `skin_pack` |
| **增强 M6** | 轻量 CNN（ONNX，&lt;5MB） | 自建标注集 |

输出：`tile_id` + `confidence ∈ [0,1]`。

**类别空间：** 与 `engine.tile` 一致（如 `1w`…`9s`）；暗杠牌背 → `back` 不计入 hand 逻辑张，副露 kind 另判。

##### F. 三类区域的专用解析

**F1 自家手牌 `hand_strip`**

```text
crop(self_hand ROI)
  → 稳定门控
  → 检测 13 或 14 个 bbox（左→右排序）
  → 逐框分类
  → 若 conf 均 ≥ τ_hand 且张数 ∈ {13,14} → 更新 obs.players[self].hand
  → 否则：HUD 高亮 conf 最低的 1–3 张，用户点选纠正（点状 C0）
```

| 参数初值（可配） | 含义 |
|------------------|------|
| `τ_hand = 0.85` | 低于此不自动采纳 |
| `τ_hand_force = 0.70` | 可「暂用」但标黄 |

**F2 弃牌河 `discard_river`（差分是关键）**

不每帧全量重识别整河（贵且易抖），而用 **状态机 + 增量**：

```text
state.rivers[seat] = ordered list[tile_id]   # 已确认
每帧:
  若 unstable: skip
  检测 ROI 内所有牌框 → 分类得 multiset M
  与 state 的 multiset 比:
    新增 1 张且 conf≥τ_river → append 事件 discard(seat,tile)
    新增多张 → 可能动画残留：推迟 1–2 帧再比
    减少张数 → 异常（UI 折叠/重绘）：触发 full_rescan 或用户确认
  last_discard ROI 若存在且高置信 → 校正 last_discard / seat
```

| 难点 | 对策 |
|------|------|
| 纵向/横向不同家布局 | 每 seat 独立 ROI + 阅读方向（ltr/ttb）写进 profile |
| 牌重叠 | 允许只读「最上层」；张数用手牌+副露守恒反推 |
| 谁打的 | 优先 last_discard 高亮区；否则根据「哪条河 multiset +1」 |

**F3 副露 `meld_area`**

```text
检测 ROI 内「牌组块」（间隙聚类）
每块:
  n = 牌数
  tiles = 分类结果
  kind 启发式:
    n==3 且全同 → peng
    n==4 且全同 → gang_ming / 若含 back → gang_an
    n==3 且顺子 → chi（若规则允许；成都血战通常无吃则标 unknown 请确认）
  conf 低或 kind 歧义 → HUD「副露待确认」点选 kind（不要求重录牌面）
```

##### G. 事件日志与 CoachObservation 合成

| 事件 | 对 obs 的影响 |
|------|----------------|
| `hand_snapshot(tiles)` | 覆盖 self.hand |
| `discard(seat, tile)` | append discards；更新 last_* |
| `meld_set(seat, kind, tiles)` | 替换/追加该 seat 副露块 |
| `dingque(seat, suit)` | 点状 UI 或识别角标（首发可手动一点） |
| `phase_hint(...)` | 14 张手牌偏 discard；有 last_discard 且非自己回合偏 response |

每 N 帧或每次事件后：`validate()` → 通过才 `policy_bridge.decide()`。

##### H. 置信度与降级策略（替代「整副 C0」）

| 情况 | 行为 |
|------|------|
| 手牌 1 张 conf 低 | 只纠这一张（27 键或最近邻候选 top-3 点击） |
| 河增量 conf 低 | 不 append；下一帧再试；超时提示「点一下是谁打出」 |
| 守恒打破 | 冻结 Policy；提示 full_rescan 或回退上一稳帧 |
| 连续 5 帧 unstable | 暂停识别，显示「等待动画结束」 |
| 用户按 F5 | 强制全 ROI 重扫 |
