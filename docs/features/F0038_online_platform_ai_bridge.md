## 0. 结论摘要（先读）

| # | 结论 |
|---|------|
| 1 | **主流线上血战/川麻对战**集中在腾讯系（欢乐麻将）、竞技世界（JJ 麻将）、微信小游戏/独立川麻 App 合集；**几乎无对个人开发者开放的「官方 Bot API」**。 |
| 2 | 将本项目 AI（`rule_ai` / Humanlike v2）**直接接入商业平台自动打牌**，若走协议逆向 / 模拟点击 / 内存注入，**高度可能违反用户协议与相关法规**，本仓库**不采纳为实现目标**。 |
| 3 | **技术上可行且合规的路径**优先：① **自建/内嵌联网对战**（本引擎权威）→ ② **官方/商务合作 AI 接口**（B2B）→ ③ **教练/旁路 HUD**（只读提示，不代操作）→ ④ 仅作架构参考的 **MJAI 类标准协议**（日麻规则不可照搬）。 |

| 6 | **方案 C 观测采集**（对手弃牌 / 副露 / 自家手牌）：**可行**；推荐 **C0 手动/半自动录入 → C1 区域截图+模板识别 → C2 本项目自建局旁路** 递进。**禁止**内存注入与协议逆向。详见 **§4.4**。 |

## 1. 背景与目标

### 1.1 背景

本仓库是 **成都麻将 · 血战到底** 本地权威引擎 + 可插拔 AI/人类 + UI + 训练与 Humanlike v2 策略。`PLAN.md` 首版 **非目标**含网络多人实时对战服务器。用户要求评估：如何将现有 AI **接到线上主流平台并自动玩牌**。

### 1.2 文档目标

| ID | 目标 |
|----|------|
| G1 | 梳理当前**线上主流血战到底/川麻对战**形态与代表产品 |
| G2 | 分析 AI 自动接入的**技术路径、成本、风险** |
| G3 | 给出与本项目架构对齐的**分层方案与阶段路线** |
| G4 | 明确 **In / Out of Scope** 与合规边界 |

### 1.3 非目标

- 不提供任何商业 App 的逆向协议、破解、注入、批量脚本 PoC  
- 不承诺「挂机打金」或绕过反作弊  
- 本轮**不写业务代码**（待 `Approved` 且选定路径后再开实现 F/M）

## 2. 线上平台调研（公开信息）

> 棋牌市场迭代快；以下为公开应用商店/官网/百科/技术文章归纳，**非**精确市场份额。

### 2.1 产品形态

| 类型 | 特征 | 与血战到底 |
|------|------|------------|
| A. 国民级合集 App | 大 DAU、3D 牌桌、多地方玩法、真人对战 | 常含四川**血流/血战** |
| B. 川麻垂直 / 小游戏 | 微信小游戏、独立 App、方言 | 更贴近四川本地规则 |
| C. 竞技赛事向 | 赛制、奖金/积分 | 如 JJ 麻将赛事 |
| D. 单机 / 弱联网 | 本地 AI | 非主流「线上对战」 |
| E. 国际/日麻平台 | 天凤、雀魂 | **规则非川麻**；AI 协议生态可作架构参考 |

### 2.2 代表平台

| 平台 / 产品 | 运营（公开） | 模式要点 | 对第三方 AI 接入（公开层） |
|-------------|--------------|----------|----------------------------|
| **欢乐麻将全集** | 腾讯 | 真人对战；四川血流/血战、打缺门、刮风下雨等 | **无公开 Bot API**；强反作弊预期 |
| **JJ 麻将** | 竞技世界 | 含四川血战等地方玩法；赛事 | 同上 |
| **四川麻将血战到底（微信小游戏等）** | 多家 | 轻量社交房 | 闭源加密常见 |
| **人人麻将** 等 | 独立发行 | 血流/血战/红中等 | 闭源 |
| **禅游等渠道川麻 App** | 禅游等 | 定缺、一胡到底等 | 闭源 |
| **蜀山四川麻将** 等 | 区域棋牌 | 好友房、血流红中 | 闭源 |
| **兜来玩麻将**（快手案例） | 快手 | 血战/血流等；**平台自研 AI** 填匹配/代打 | **内部能力**，非第三方 SDK |
| **天凤 / 雀魂** | 日麻生态 | Suphx、Mortal、MahjongCopilot | 有研究/第三方协议；**规则不适配本引擎** |

检索结论：**无面向个人开发者的「成都血战官方实时出牌 Bot SDK」**。

### 2.3 行业技术共性

```text
客户端 → 加密长连接/WS → 网关+反作弊 → 房间/匹配/结算 → 服务端权威状态
```

- 服务端权威（与本项目 `engine/` 角色类似，但状态在对方）  
- 私有协议与动作编码 ≠ 本仓库 `Action` / `GameState`  
- 反作弊：时序、多开、脚本特征、设备指纹  
- 同名「血战」在换三张、封顶、查叫、杠分上可能与本引擎配置有差异

## 4. 方案矩阵

### 4.1 统一抽象

```text
 Policy (rule_ai / humanlike / 人类)
        ▲ ActionRequest / Decision
 OnlineBridge / Adapter
        ▲
 SelfHostRoom | Official API | （禁止）逆向客户端
```

**决策层不依赖 UI；Adapter 负责观测翻译与动作回写。**

### 4.2 方案 A — 自建线上对战（**推荐主路径**）

| 项 | 内容 |
|----|------|
| 思路 | 房间服 + 客户端；权威=`engine`；席位接 AI/人类 |
| 自动玩牌 | 全 AI 或 1 人 3 AI，天然合规 |
| 优点 | 规则一致、可复现 `game_id`、可产训练日志 |
| 缺点 | 无现成 DAU |
| 粗估 | 好友房 MVP 数周；公网匹配数月 |

子路径：**A1 局域网/好友房** → **A2 公网匹配**。

### 4.3 方案 B — 官方/商务合作

| 项 | 内容 |
|----|------|
| 思路 | 厂商提供匹配填充/掉线代打 API；本侧只跑 Policy 服务 |
| 先例 | 快手等业务内多玩法麻将 AI（公开分享，**非**对外开放） |
| 优点 | 合规商用 |
| 缺点 | 商务门槛 |

建议接口形态：`observation + legal_actions → action`（规则集 ID 必填）。

### 4.4 方案 C — 教练 / 旁路 HUD（主写：观测与采集）

| 项 | 内容 |
|----|------|
| 思路 | **不代用户点击出牌**；只根据「人类玩家可见的公开/私有信息」给出推荐（对齐 F0011 / Humanlike 决策） |
| 对照 | 日麻生态「指导 HUD」形态（架构参考；对接商业客户端可能仍触及 ToS，产品需免责） |
| 定位 | **教学 / 复盘 / 训练数据采集**；与方案 D/E 外挂切割 |
| 核心输入 | ① 对手弃牌序列 ② 各家副露 ③ 自家手牌（+ 可选：定缺、墙剩余、当前阶段） |
| 核心输出 | 推荐出牌 / 碰杠胡建议 + 理由；可选 JSONL 采集日志 |

#### 4.4.1 要采集的三类信息（与本项目 view 对齐）

教练 AI 并不需要对方服务器的完整 `GameState`，只需 **座位视角** 下人类本就可看见的字段。映射到本仓库 `PlayerView` / `build_observation` 习惯：

| 信息类 | 可见性 | 建议内部结构（逻辑牌 ID，如 `3w`/`9p`/`1s`） | 用途 |
|--------|--------|-----------------------------------------------|------|
| **自家手牌** | 仅自己可见 | `self.hand: list[str]`（13 或 14 张，已排序可选） | 向听、进张、推荐出牌、防放炮 |
| **对手弃牌** | 公开 | `players[s].discards: list[str]`（按时间序） | 读河、危险度、F0010 类推断 |
| **各家副露** | 公开（含自己） | `players[s].melds: list[{type, tiles}]` | 牌山剩余、形状、是否门清 |
| （强烈建议）定缺 | 公开或半公开 | `players[s].dingque: "wan"\|"tong"\|"tiao"\|null` | 川麻必备 |
| （建议）最后打出 | 公开 | `last_discard` + `last_discard_seat` | 响应阶段（碰/杠/胡） |
| （可选）墙剩余 | 公开 UI 常有 | `wall_remaining: int` | 中后期策略 |
| （可选）阶段 | 推断或录入 | `phase: exchange\|dingque\|discard\|response\|…` | 调用哪类 decide |

**不采集 / 不猜测进模型输入的：** 对手未公开手牌、牌山精确顺序、对方客户端私有协议字段。

#### 4.4.2 可行性总表

| 采集通道 | 自家手牌 | 对手弃牌 | 副露 | 准确率潜力 | 实时性 | 合规/ToS | 工程难度 | 方案 C 建议 |
|----------|----------|----------|------|------------|--------|----------|----------|-------------|
| **C0 手动/半自动录入** | 高 | 高 | 高 | ★★★★★ | 慢（2–10s/事件） | **最好**（用户自报） | 低 | **P0 必做** |
| **C1 区域截图 + 视觉识别** | 中高 | 中高 | 中 | ★★★☆（依赖 UI 稳定） | 中（0.3–2s） | 灰区：只读屏幕、不注入；**仍可能违反部分游戏 ToS** | 中高 | **P1**（限定「用户本机、教学、不代打」） |
| **C2 本项目自建局旁路** | 完美 | 完美 | 完美 | ★★★★★ | 实时 | **完全合规** | 低（已有协议） | **P0 并行**（验证策略与 UI） |
| **C3 官方观战/导出 API** | 视接口 | 视接口 | 视接口 | ★★★★★ | 实时 | 合规 | 依赖商务 | P3 |
| **C4 协议逆向 / 内存** | — | — | — | — | — | **禁止** | — | **Out of Scope** |

**可行性结论：**

1. **仅就「把三类信息喂给本项目 AI」而言：完全可行**——决策层只吃标准化 `CoachObservation`，与来源无关。  
2. **若数据源是商业 App 画面：** 技术可行度中等（UI 多分辨率/3D/动画），**产品合规需用户知情同意 + 不做自动操作**；本仓库实现时默认只交付 **C0 + C2**，C1 作为可选模块且文档标明 ToS 自担。  
3. **推荐产品闭环：** 用 **C2** 打磨推荐质量 → **C0** 支持外站慢速教练 → 再评估是否值得做 **C1**。

#### 4.4.3 目标数据模型（CoachObservation v0）

```text
CoachObservation
├── schema: 1
├── ruleset_id: "chengdu_blood_v1"
├── self_seat: 0..3
├── phase: "discard" | "response" | "dingque" | "exchange" | ...
├── wall_remaining: int | null
├── last_discard: tile_id | null
├── last_discard_seat: int | null
└── players: [0..3]
      ├── seat: int
      ├── dingque: suit | null
      ├── hand: [tile_id]          # 仅 self_seat 非空；他家 [] 或省略
      ├── discards: [tile_id]      # 时间序
      ├── melds: [{ "kind": "peng"|"chi"|... , "tiles": [tile_id] }]
      └── hand_count: int | null   # 他家仅公开张数时
```

与本项目衔接：

| 步骤 | 动作 |
|------|------|
| 1 | `CoachObservation` → 尽量填满 legacy `view` dict（与 `filter_state_for_seat` 字段同构的子集） |
| 2 | 由 **轻量合法性模块** 在「已知公开信息」下枚举可行动作（出牌=手牌任一；响应=对 `last_discard` 的碰/杠/胡/过）——**不要求**完整引擎权威状态 |
| 3 | 构造 `ActionRequest` → 调用 `rule_ai` / Humanlike / F0011 顾问 |
| 4 | HUD 只展示 `Decision` + 理由；**不**写回外部游戏 |

> 完整 `engine.GameState` 在 C0/C1 下**通常无法重建**（缺墙与他手）。因此方案 C 的 Policy 应支持 **「部分观测模式」**：输入不完整时降级（仅向听/危险度启发式），禁止假装拥有 oracle。

#### 4.4.4 三类信息的采集细则

**A. 自家手牌**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 点选面板 | 27 种牌（万筒条 1–9）棋盘 + 张数；支持「摸打同步」：摸一张 / 打一张 | 用户点错 |
| C0 快捷 | 导入字符串 `123m456p789s11m` 类编码 | 编码约定要固定 |
| C1 视觉 | 标定「手牌条」ROI；模板匹配 / 分类器识别每张牌面；14 张时含摸牌位 | 遮挡、金框、缩放、主题皮肤 |
| C2 | 直接读 `build_observation(...).view` 中 self hand | 无 |

**B. 对手弃牌（河）**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 | 四家河分区；每打出一张点一次，或批量「追加弃牌」 | 漏记、顺序错 |
| C0 事件流 | 只记「当前打出」+ 自动 append 到对应 seat | 用户忘点「谁打的」 |
| C1 | 标定三家/四家弃牌区 ROI；检测新增牌面相对上一帧 diff | 动画飞牌、重叠、缩略 |
| C2 | `players[s].discards` 全量 | 无 |

**C. 副露**

| 方式 | 步骤要点 | 风险/误差 |
|------|----------|-----------|
| C0 | 选择 seat + 类型（碰/明杠/暗杠/直杠）+ 相关牌 | 暗杠显示因平台而异 |
| C1 | 副露区 ROI；识别副露块数量与牌面；类型用布局启发式（3 张碰 / 4 张杠） | 暗杠牌背、方向 |
| C2 | `players[s].melds` | 无 |

**公开信息一致性校验（采集后必跑）：**

| 校验 | 规则（血战 108 张） |
|------|---------------------|
| 张数守恒 | 每张逻辑牌全局可见计数 ≤ 4 |
| 手牌张数 | 行牌中自己通常 13 或 14；与 phase 一致 |
| 副露耗牌 | 碰 3、杠 4 等从「可能剩余」中扣除 |
| 弃牌不回手 | 已进河的牌不应再出现在 self.hand（用户修正时警告） |

#### 4.4.5 推荐架构（方案 C 专用）

```text
┌──────────────────────────────────────────────────────────┐
│  Coach Capture Layer                                       │
│  C0 UI 录入 │ C1 ScreenPipe(可选) │ C2 LocalEngineTap       │
└────────────────────────────▲─────────────────────────────┘
                             │ CoachObservation (JSON)
┌────────────────────────────┴─────────────────────────────┐
│  Normalize + Validate                                      │
│  tile 编码统一 · 守恒校验 · phase 推断 · 差分事件 EventLog  │
└────────────────────────────▲─────────────────────────────┘
                             │ PartialView / ActionRequest
┌────────────────────────────┴─────────────────────────────┐
│  Coach Policy                                              │
│  F0011 顾问 · rule_ai · humanlike（部分观测模式）           │
└────────────────────────────▲─────────────────────────────┘
                             │ Decision + reasons（只读）
┌────────────────────────────┴─────────────────────────────┐
│  Coach HUD                                                 │

```

**硬规则：** Capture → Policy → HUD 单向；**禁止** HUD/Policy 回调「自动点击外部窗口」。

#### 4.4.6 具体实施步骤（工程分解）

##### 阶段 C-P0 — 数据合同与手动教练（约 3–7 人日）

| 步 | 动作 | 产出 | 验收 |
|----|------|------|------|
| C-P0.1 | 冻结 `CoachObservation` JSON schema + tile 编码表（与 `engine.tile` 一致） | `docs` + 示例 JSON | 样例通过 schema |
| C-P0.2 | 实现 `normalize_coach_obs()`：别名、排序、校验守恒 | `players/coach/` 或 `protocols/coach_obs.py` | 单测：缺牌/多牌/错误副露 |
| C-P0.3 | 实现 `partial_legal_actions(obs)`：discard/response 最小集 | 同上 | 与完整引擎在「信息完备自建局」上对照 |
| C-P0.4 | 接线 Policy：obs → `Decision`（先 `rule_ai` 或 F0011） | 库函数 + CLI `coach-decide` | 给定样例输出稳定 |
| C-P0.5 | **手动录入 UI**（Tk 即可）：手牌网格、四家河、副露编辑、定缺、谁刚打出 | `tools/coach_panel` 或座位窗精简模式 | 用户 1 分钟内录入一副可用局 |
| C-P0.6 | HUD 展示推荐 + 理由；导出 `coach_session.jsonl` | 文件落盘 | 可复盘 |

##### 阶段 C-P1 — 本项目旁路（C2，约 2–4 人日）

| 步 | 动作 | 产出 | 验收 |
|----|------|------|------|
| C-P1.1 | 在本地 `play/human` 局中订阅 observation（已有座位协议） | `CoachObservation` 自动填充 | 与座位窗手牌/河一致 |
| C-P1.2 | 主窗或座位窗「教练条」：实时推荐，不代替 human 出牌 | UI 开关 | 人类仍手动出牌 |
| C-P1.3 | 采集 JSONL：每步 obs + decision + 人类实操（若有） | 训练/分析语料 | 字段齐全 |

> C2 不解决「外站」问题，但验证 **采集字段是否够 AI 好用**，避免过早上 C1。

##### 阶段 C-P2 — 事件化采集 UX（约 3–5 人日）

| 步 | 动作 | 产出 | 验收 |
|----|------|------|------|
| C-P2.1 | 改为「事件流」录入：`draw` / `discard(seat,tile)` / `peng` / `gang` / `hu` | Event → 累积 obs | 漏事件可撤销 |
| C-P2.2 | 快捷键/大按钮：「对家打出=当前选中牌」 | 降负担 | 河序正确 |
| C-P2.3 | 校验失败时内联红字，禁止算牌直到修复 | UX | 无静默坏状态 |

##### 阶段 C-P3 — 可选视觉管线 C1（约 2–6 周，高风险）

| 步 | 动作 | 产出 | 验收 |
|----|------|------|------|
| C-P3.0 | **合规门禁**：产品文案「教学辅助、不代打、用户自担 ToS」；默认关闭 | 文档+开关 | 无默认联网上传截图 |
| C-P3.1 | 布局标定工具：用户框选「手牌区 / 四家河 / 副露区」存 profile | `coach_layout.json` | 多分辨率可加载 |
| C-P3.2 | 截帧源：系统 ScreenCapture（macOS/Windows 权限）；固定窗口标题可选 | 帧序列 | 5 fps 足够 |
| C-P3.3 | 牌面识别：先用本项目 `assets/tiles/*` 模板匹配；再考虑小 CNN | `tile_id` + conf | 手牌 top-1 ≥ 95%（固定皮肤） |
| C-P3.4 | 差分：河区新增牌 → 自动 `discard` 事件；副露区块数变化 → 提示用户确认类型 | 半自动 | 误检需一键撤销 |
| C-P3.5 | 皮肤/3D 失败降级：置信度低则弹「请手动确认」回 C0 | 混合模式 | 不硬猜 |

**C1 明确不做：** 后台注入、隐藏窗口读内存、绕过登录、自动点击出牌。

##### 阶段 C-P4 — 质量与数据闭环

| 步 | 动作 |
|----|------|
| C-P4.1 | 黄金样例集：20 局手动 obs + 期望推荐类别（不必唯一最优） |
| C-P4.2 | 指标：录入耗时、识别准确率、推荐采纳率（若用户标注） |
| C-P4.3 | 与 Humanlike / F0011 回归：部分观测 vs 全观测分数差 |

#### 4.4.7 与 F0010 / F0011 的关系

| 模块 | 在方案 C 中的角色 |
|------|-------------------|
| 弃牌河 | F0010 对手手牌推断、危险度 |
| 副露 + remain | 进张与剩余张数 |
| 自家手牌 | 向听、F0011 综合出牌 |
| 缺门 | 斩色/定缺约束 |

采集越完整，F0010/F0011 越接近本地座位窗能力；**缺他手时预测方差大**，HUD 应显示「信息不足」而不是虚假精确率。

### 6.1 DecisionService API 草案

```json
// Request
{
  "protocol": 1,
  "ruleset_id": "chengdu_blood_v1",

  "phase": "discard",
  "view": {},

}

{
  "action": { "type": "discard", "tile": "3w" },
  "reason": "rule_ai:shanten",

}
```
