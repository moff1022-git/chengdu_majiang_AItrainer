# Humanlike并发内存与吞吐审计

- 日期：2026-08-05
- 范围：正式`nonhuman_optimized`入口，固定数据集前12局，四座Humanlike
- 结论：当前线程并发不提升吞吐，但显著提高峰值RSS；大批量线程运行存在被系统外部终止风险。

## 测量结果

|workers|局数|耗时(s)|峰值RSS(MiB)|相对单线程RSS|
|---:|---:|---:|---:|---:|
|1|12|41.843|56.64|1.00x|
|2|12|42.147|77.50|1.37x|
|5|12|42.830|102.91|1.82x|

100局验证中workers 10和5均被执行环境直接终止，无Python异常和结果文件；workers 1以341.67秒完成100/100。

## 原因判断

- Humanlike决策主要是Python CPU计算，线程受到GIL限制，当前样本没有并行加速。
- 每个并发牌局同时持有四个玩家、认知/审计状态和牌局对象，worker增加使存活对象线性叠加。
- 因此线程数增加造成RSS上涨而吞吐不变；较大批次叠加执行环境内存门限后可能被外部kill。

## 建议

- 正式Humanlike批跑默认`threads=1`；现有线程选项暂不改变，以免超出本轮只审计范围。
- 后续另立Approved规格，将CPU并行迁移为受控多进程，并按可用内存计算worker上限。
- runner应在启动提示中区分纯Python Humanlike与轻量AI的推荐并发值。
